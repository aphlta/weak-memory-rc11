# 弱内存自动验证的实际工作拆解

这份文件不再停留在“研究方向”层面，而是把后续真正要做的事拆成可执行任务。

## 1. 先做什么

如果你要把这个题目从开题推进到“能写代码、能跑实验、能答辩”，最实际的工作是 4 块：

1. `程序表示`
2. `候选执行生成`
3. `性质检查`
4. `状态空间约简`

这 4 块的关系是：

- 没有程序表示，就没法把论文中的语义对象变成代码对象
- 没有候选执行生成，就没法真正讨论 weak memory 下的可能行为
- 没有性质检查，就做不出 race / assertion 的结果
- 没有状态空间约简，工具只能跑很小的例子，论文创新点也立不住

## 2. 每一块要做的实际工作

### 2.1 程序表示

需要先定义一个最小输入语言，而不是一上来支持完整 C/C++。

建议最小支持这些操作：

- `load`
- `store`
- `assert_eq`
- `fence`

每个内存访问至少要带这些字段：

- `loc`
- `atomic`
- `order`
- `thread`
- `program-order index`

在代码里，对应就是一个 `Event` 结构体或类。

### 2.2 候选执行生成

这是原型的核心。

对每个 `load`，需要枚举它可能从哪个 `write` 读到值，也就是构造 `reads-from` 关系。对于简化原型，最直接的方法是：

1. 找到同一地址上的所有可能写入
2. 排除同线程里发生在该 `load` 之后的写入
3. 为每个 `load` 枚举一个候选写入来源
4. 组合得到一个候选执行

这一步在代码里通常表现为：

- `writes_by_loc`
- `reads_from_candidates(load)`
- `product(*candidates_per_load)`

### 2.3 性质检查

原型阶段最值得先做的是两类性质：

#### `data race`

判断规则可以先简化为：

- 两个线程
- 同一地址
- 至少一个是写
- 至少一个是非原子访问
- 二者之间不存在 `happens-before`

#### `assertion violation`

做法是：

1. 根据当前执行的 `reads-from` 结果，给每个 `load` 赋值
2. 按线程内程序顺序解释变量
3. 遇到 `assert_eq` 就判断是否失败

### 2.4 状态空间约简

这是后面真正能写成创新点的部分。现在这个原型先实现最基本的枚举，但你后面可以沿着下面几条继续做：

1. `等价执行去重`
2. `基于地址的局部剪枝`
3. `只在影响断言的 load 上展开`
4. `对无关线程片段做 partial order reduction`
5. `用 execution graph signature 做 memoization`

## 3. 这份原型已经做了什么

当前目录下的原型代码已经实现了一个 `RC11/RA 风格的简化验证器`，支持：

- JSON 输入程序
- 事件建模
- `reads-from` 枚举
- `release/acquire` 风格的 `synchronizes-with`
- `happens-before` 传递闭包
- `data race` 检测
- `assert_eq` 检测

这意味着它已经不是“选题描述”，而是一个真正能跑的研究起点。

## 4. 代码方法

这份原型当前使用的是最容易解释、最适合开题阶段的实现路线：

### `方法一：显式执行枚举`

优点：

- 容易实现
- 容易解释
- 便于和论文中的执行图对应

缺点：

- 状态空间增长快
- 只能跑小规模示例

### `方法二：图关系推导`

当前代码里显式构造了这些关系：

- `po`：program order
- `rf`：reads-from
- `sw`：synchronizes-with
- `hb`：happens-before

这是因为后续要做的 race 检查和 assertion 检查，都依赖这些关系。
